Client web ACP & Voice Gateway

Comment une conversation texte dans le navigateur devient une conversation vocale locale, sans dupliquer la logique de session de l'agent.

01 En une phrase

Le serveur Node existant (server/acp-bridge.js) jouait déjà le rôle de Conversation Controller pour le client texte : il spawn l'agent ACP, expose une API REST et diffuse ses réponses en SSE. Le Voice Gateway (local, Python) se branche dessus comme un client HTTP+SSE de plus — il ne parle jamais directement à l'agent.

04 Ce qui est fait

Voice Gateway (local)

  • fait AudioIO full-duplex + PTT clavier → WAV
  • fait Whisper local + filtre anti-hallucination
  • fait Text Pipeline (Speakable + Segmenter) + Player
  • fait TTS : Piper, macOS say, relais navigateur
  • fait Soak test 50 tours (0 fuite, 0 état incohérent)

Intégration web

  • fait Bouton « Mode vocal » + sélecteur de voix dans l'UI
  • fait Pont HTTP+SSE (aucune dépendance ACP dupliquée)
  • fait Instance unique forcée (micro/HP = ressource physique)
  • à faire Annonce vocale sur demande de permission (§12.3)
  • à faire VAD / barge-in / AEC (étapes 5+ de la spec)

05 Décisions qui comptent

  • Pas de second client ACP. Le Voice Gateway parle HTTP+SSE au serveur Node existant plutôt que de spawn son propre agent — zéro duplication de la logique de session, zéro nouvelle dépendance réseau côté Node.
  • Une seule instance vocale, globale. Le micro et les haut-parleurs sont une ressource physique unique de la machine : démarrer une session vocale tue automatiquement la précédente, quelle que soit sa connexion ACP d'origine.
  • Un seul tour actif à la fois. Pas de barge-in dans cette version — un nouveau PTT pendant qu'un tour est en cours est ignoré plutôt que d'interrompre l'agent.
  • Le rendu vocal est interchangeable, pas la capture. Piper, say et navigateur partagent le même pipeline PTT → Whisper → agent ; seule la dernière étape (parler la réponse) change d'implémentation.
