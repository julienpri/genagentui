Comment une conversation texte dans le navigateur devient une conversation vocale locale, sans dupliquer la logique de session de l'agent.

01 En une phrase

Le serveur Node existant (server/acp-bridge.js) jouait déjà le rôle de Conversation Controller pour le client texte : il spawn l'agent ACP, expose une API REST et diffuse ses réponses en SSE. Le Voice Gateway (local, Python) se branche dessus comme un client HTTP+SSE de plus — il ne parle jamais directement à l'agent.

03 Détail par composant

Les cinq dossiers du repo qui participent à une conversation vocale, dans l'ordre où ils entrent en jeu. Chacun n'a qu'un seul rôle ; aucun n'importe la couche du dessus.

🖥️ public/

frontend

Vanilla HTML/CSS/JS, aucun framework, aucun build. Affiche l'état, envoie les prompts, ne capture ni ne joue jamais d'audio lui-même — sauf speechSynthesis quand la voix « navigateur » est choisie.

  • index.htmlpanneaux (sessions, config, commandes, plan), composer, modale de permission, panneau debug
  • app.jsstate global + objet agent (initialize/prompt/cancel/startVoice…) + dispatcher SSE (connectEvents())
  • style.cssthème, pas de dépendance externe

Parle à : server/ (fetch REST + EventSource). Ne connaît ni l'agent ACP ni le Voice Gateway par leur nom.

🖧 server/

backend Node, zéro dépendance npm

Le Conversation Controller au sens de la spec voix — il existait avant l'intégration vocale et n'a pas changé de rôle, juste gagné deux routes.

  • server.jshttp.createServer, table ROUTES, endpoint SSE /api/events (ping toutes les 25s)
  • acp-bridge.jsclasse Connection (1 par agent connecté) ; startVoice/stopVoice spawn/kill web_session.py, 1 seule instance globale (activeVoiceConnectionId)

Parle à : acp/ (spawn l'agent), voice-gateway/controller/ (spawn, via les mêmes routes REST que le navigateur).

🔌 acp/

client JSON-RPC générique

Parle le protocole ACP sur stdio. Ne sait rien de la voix, rien du web — utilisé tel quel par server/acp-bridge.js.

  • client.jsACPClient — spawn l'agent, JSON-RPC newline-delimited, EventEmitter (frame/notification/agent_request/exit)
  • protocol.jsconstantes de méthodes, SESSION_UPDATE_KINDS, builders de messages

Utilisé par : server/acp-bridge.js uniquement.

🎙️ voice-gateway/voice_gateway/

package Python, importable seul

Le cœur audio local. N'importe jamais controller/ — il ignore totalement l'existence d'ACP, du web, ou de Node (cf. spec §18).

  • core/types.py, cancel.pyAudioFormat, AudioChunk, Transcript, CancelToken
  • audio/audio_io.pyAudioIO — flux sounddevice.Stream full-duplex unique, callback non-bloquant
  • audio/resampler.pyresample_to() (soxr) — format interne 16kHz mono int16
  • audio/player.pyPlayer — file de lecture, pull() non bloquant côté callback audio
  • stt/faster_whisper.py, filter.pyWhisperSTT local + TranscriptFilter anti-hallucination
  • text/segmenter.py, speakable.py, pipeline.pyphrases complètes en streaming, markdown → texte prononçable, speak_sentence() partagé
  • tts/piper.py, say.pydeux implémentations interchangeables de TTSProvider

Parle à : le matériel audio local uniquement (sounddevice, modèles sur disque). Aucun réseau.

🧩 voice-gateway/controller/

orchestrateur — connaît ACP ET audio

Le seul endroit qui connaît à la fois voice_gateway/ et le serveur Node. Deux entrées : le CLI de test (Fake Agent) et le mode web réel.

  • web_session.pyspawné par Node ; PTT (pynput) → handle_voice_turn → on_sse_event → finish_turn, classe Turn (un tour actif à la fois)
  • acp_http_client.pyACPHttpClient — POST /api/prompt, SSE /api/events, POST /api/voice/event

Parle à : server/ (HTTP+SSE) et voice_gateway/ (import direct, même process Python).

  • fait Text Pipeline (Speakable + Segmenter) + Player
  • fait TTS : Piper, macOS say, relais navigateur
  • fait Soak test 50 tours (0 fuite, 0 état incohérent)

Intégration web

  • fait Bouton « Mode vocal » + sélecteur de voix dans l'UI

  • fait Instance unique forcée (micro/HP = ressource physique)
  • à faire Annonce vocale sur demande de permission (§12.3)
  • à faire VAD / barge-in / AEC (étapes 5+ de la spec)

07 Décisions qui comptent

  • Pas de second client ACP. Le Voice Gateway parle HTTP+SSE au serveur Node existant plutôt que de spawn son propre agent — zéro duplication de la logique de session, zéro nouvelle dépendance réseau côté Node.
  • Une seule instance vocale, globale. Le micro et les haut-parleurs sont une ressource physique unique de la machine : démarrer une session vocale tue automatiquement la précédente, quelle que soit sa connexion ACP d'origine.
  • Un seul tour actif à la fois. Pas de barge-in dans cette version — un nouveau PTT pendant qu'un tour est en cours est ignoré plutôt que d'interrompre l'agent.
  • Le rendu vocal est interchangeable, pas la capture. Piper, say et navigateur partagent le même pipeline PTT → Whisper → agent ; seule la dernière étape (parler la réponse) change d'implémentation.
